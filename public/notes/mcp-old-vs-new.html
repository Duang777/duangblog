同一件事，两种模型

左边是 2025-11-25 的 MCP，右边是草案。差别几乎都能从「服务端还记不记得你」这一条推出来。

旧：有状态的会话

2025-11-25 及更早

  • 先握手再干活initialize + notifications/initialized，版本和能力只协商一次。
  • 会话 ID 贯穿全程Mcp-Session-Id 由服务端下发，状态存在服务端。
  • 工具列表可以因人而异同一个 server 能按会话身份返回不同的 tools/list。
  • 服务端反向请求客户端Roots、Sampling、Elicitation 都靠双向连接。
  • GET + SSE 收通知resources/subscribe，断线可用 Last-Event-ID 续传。
  • ping 保活、全局日志级别logging/setLevel 一设就是整个会话。

新：无状态的请求响应

draft

  • 没有开场白版本和能力放进每个请求的 _meta，需要探测就调 server/discover。
  • 没有会话要跨调用记东西，服务端自己签发 handle，当普通参数传。
  • 一张清单对所有人列表接口不随连接变化，要区分就拆端点。
  • MRTR 把方向反过来返回 input_required，客户端补齐信息后重试原请求。
  • subscriptions/listen 统一入口流一断请求即作废，必须用新 ID 重发。
  • ping 删除、日志按请求开保活交给传输层，默认不发 notifications/message。
为什么值得这么改

每个请求自包含之后，任意实例都能处理任意请求 —— MCP server 可以像普通 HTTP 服务那样做负载均衡、水平扩容和滚动重启。代价是幂等、重试、状态管理这些复杂度，从协议层挪到了你自己的业务代码里。
